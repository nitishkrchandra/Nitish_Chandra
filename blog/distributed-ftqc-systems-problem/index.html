Distributed fault-tolerant quantum computing is a systems problem

Why error correction, optical interconnects, and logical execution have to be designed as one system.

Quantum computers will need many reliable qubits to run useful fault-tolerant algorithms. One possible route is to connect smaller quantum processors rather than make every qubit, control line and interaction fit inside a single device. A network of quantum processing units (QPUs) could be more flexible: processors can specialize, hardware may be manufactured in smaller modules, and entanglement can enable interactions between distant qubits.

But there is a large gap between connecting quantum processors and computing reliably across them. That gap is where much of my research sits. Distributed fault-tolerant quantum computing (FTQC) is not solely a networking problem, nor solely an error-correction problem. It is a systems problem in which choices at one layer change the performance and reliability of the others. The general landscape and architectural motivations are reviewed in the distributed-quantum-computing survey by Caleffi and collaborators [1].

1. What does it mean to distribute a quantum computer?

There are at least two distinct things we might distribute: physical qubits belonging to one encoded logical qubit, or complete encoded logical qubits that interact across processors. They require different kinds of communication. In the first case, the interconnect may participate in every error-correction cycle. In the second, it can be reserved for operations between encoded blocks, allowing much of the routine correction to remain local.

To make the distinction concrete, suppose a stabilizer code uses many physical qubits to store protected logical information. Maintaining that information means repeatedly measuring stabilizers and decoding their measurement outcomes. If the code spans QPUs, some of those checks may require remote entanglement during every error-correction cycle. If instead each QPU holds a complete code block, its error correction may be mostly local, but logical operations between blocks require fault-tolerant interfaces.

Our work on architectural approaches to distributed FTQC formalizes three broad patterns [2]:

  1. Small cooperating nodes: shared multipartite entangled resources support nonlocal stabilizer measurements.
  2. One partitioned code block: most checks stay local, but checks across partition boundaries use remote operations.
  3. Separate encoded blocks: each QPU hosts one or more code blocks, while logical gates use appropriate inter-module protocols.

These architectures cannot be compared solely by counting their processors. One architecture spends entanglement on repeated syndrome extraction; another spends it largely on logical interactions. Their communication demand depends on code distance, circuit depth and the workload's pattern of logical gates.

2. How can a remote quantum interaction be implemented?

A common building block is a Bell pair shared between two modules. The network generates entanglement between communication qubits, and local gates, measurements and classical feedforward use that resource to implement a remote operation on computational qubits. This is the principle behind quantum gate teleportation.

The experimental distinction matters. In 2025, Main and collaborators demonstrated deterministic gate teleportation conditional on having successfully generated the shared entanglement between two trapped-ion modules, and used repeated remote gates within distributed circuits [3]. In September 2026, Ainley and collaborators reported remote syndrome measurements and error correction across two trapped-ion processors, including experiments involving a distributed repetition code and feedforward [4].

These demonstrations answer important physical questions. They do not, by themselves, tell us the logical error rate or resource overhead of a large encoded computation. At that scale, Bell pairs must arrive often enough to support the many checks and logical gates a fault-tolerant computation needs.

3. Why a network is not simply a long wire

On a classical network, retrying a lost packet mainly costs time and bandwidth. For a quantum computer, a failed entanglement attempt can also cause the stored computational state to wait while its physical qubits continue to accumulate errors.

For a deliberately simplified example, suppose independent entanglement attempts succeed with probability q. If we keep retrying until the first success, then the number N of attempts has a geometric distribution:

At a fixed attempt duration ta, the mean attempt time is ta/q before accounting for reset, cooling, routing and feedforward. If communication ports are shared, contention can make the actual delay longer and dependent on the schedule. Meanwhile, an encoded data block may need to keep correcting errors during that wait.

This is why I find it misleading to evaluate a link using fidelity alone. A useful interconnect is characterized by the fidelity and rate of usable entanglement, the waiting-time distribution, available communication qubits and the errors induced by the remote protocol.

4. A computation passes through several layers

In an end-to-end architecture, the information must pass through a linked chain of decisions:

01

Code and logical operationsWhat is encoded, and which protected instructions must be executed?

02

Physical placementWhere are the data qubits, ancillas and communication qubits?

03

Remote protocolsHow are nonlocal checks and logical gates implemented using entanglement?

04

Scheduling and decodingWhat waits, competes for resources and generates correlated errors?

05

Logical outcomeWhat logical failure probability, latency and hardware cost result?

Each layer constrains the next, but feedback matters too. A slow schedule increases memory noise, which might require a larger code. A larger code requires more checks, which increases network demand. This feedback is a reason to perform architecture-aware co-design rather than independently optimize a compiler, decoder and quantum switch.

Our optically networked trapped-ion work connects remote entanglement generation, spatial and temporal multiplexing, qubit and memory noise, and the preparation of a protected measurement-based resource state [5]. More recently, our network-constrained FTQC framework studies how finite generation rates, communication qubits and bandwidth contention change execution time and error estimates [6]. Separate work on quantum-switch policies shows that storing, distilling and swapping Bell pairs involve their own timing and fidelity tradeoffs [7].

5. What should we optimize?

There is no single metric that captures distributed FTQC. Minimizing remote operations may produce a poor schedule. Maximizing Bell-pair fidelity may reduce throughput. Minimizing physical-qubit count may leave too few ports for timely correction. These tradeoffs depend on the intended logical workload: a quantum memory and a computation requiring frequent remote gates can favor very different partitions and communication designs.

A more informative comparison should report at least logical error per operation or cycle, completion time, communication overhead and total hardware resources. Which design is preferable depends on the intended workload and target reliability. In particular, quantum-memory performance and the cost of universal logical computation should not be conflated.

What should a network service promise?

A useful architecture boundary is an entanglement-delivery service: the network supplies pairs with specified quality, resource use and completion-time statistics; the fault-tolerant instruction requests those pairs and declares how they will be used. Such a contract makes the hardware model replaceable without pretending the remote operation has zero latency.

Imagine two modules connected by a switch. Delivering one end-to-end pair might require generating two elementary links and performing swapping; another system may directly connect the modules. Their physical mechanisms differ, but both can be evaluated in terms of how often they deliver useful entanglement, what error correlations survive, and what other work must wait.

In a practical benchmark I would fix the logical task and target reliability, then report qubit occupation, pairs consumed, mean and tail latency, and the failure probability of the encoded computation. This also separates useful quantum memory from universal quantum processing: an architecture excellent at storing distributed logical qubits may still have expensive nonlocal logical gates.

My perspective: connecting the pieces

I see an opportunity to develop a cross-layer methodology in which a logical computation is lowered into fault-tolerant primitives, mapped onto a modular architecture, scheduled against a realistic entanglement service, and evaluated with a noise model reflecting how those operations were actually carried out.

The longer-term goal is a machine that is not merely network connected, but demonstrably fault tolerant at the logical level. The key research question is therefore not “Can two QPUs interact?” It is “How can we arrange the complete computation so that the network enables scalability without erasing the protection provided by quantum error correction?”
