Distributed fault-tolerant quantum computing is a systems problem

Why the interconnect and error-correcting code must be designed together

The attraction of a modular quantum computer is straightforward: rather than scaling a single processor indefinitely, smaller quantum processing units (QPUs) can be connected through entanglement. The difficult question is whether such a collection can execute protected logical computations efficiently. Establishing physical connectivity is not equivalent to scalable fault tolerance.

What is being distributed?

A logical qubit must be maintained through repeated syndrome measurements. In one architecture, a single error-correcting code is partitioned across processors, so some stabilizer measurements require nonlocal operations. In another, each processor holds a complete logical code block and the network supplies interactions between blocks. These architectures have different communication burdens. Our overview of distributed architectures examines these differences and their entanglement costs.

The physical link may supply Bell pairs through a probabilistic heralded process. If pairs take time to arrive, the syndrome schedule can stall. Memory decoherence, port contention and classical feedforward delays can affect the eventual logical error rate. A link characterized only by its Bell-pair fidelity is therefore an incomplete description.

From a remote link to a fault-tolerant computation

Optically connected trapped-ion modules have demonstrated distributed quantum computing over a network link. This is an important experimental capability, but the next design layer must translate entanglement into repeated logical operations. Our multiplexed trapped-ion architecture studies a particular measurement-based route using protected cluster states and relates optical, gate and memory imperfections to fault-tolerance conditions. More recent analysis of network constraints similarly emphasizes the interaction between entanglement rates, communication resources and code operation.

A cross-layer research agenda

I find it useful to regard the system as a sequence of decisions: choose a code and its logical instruction set; partition data and ancillary resources; select physical implementations of remote operations; schedule communication and syndrome extraction; then calculate logical reliability and execution time. The dependencies run in both directions. Changing the schedule changes memory exposure, which changes the effective noise model and sometimes the best code configuration.

The central research challenge is to compare architectures using logical error, runtime and physical-resource overhead together. Remote gates are enabling primitives; reliable distributed logical computation is the actual objective.
