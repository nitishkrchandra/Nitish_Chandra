A remote logical gate is more than a remote physical gate

Distributed lattice surgery, logical parity measurements and noisy interfaces

A remote physical CNOT can be performed using en­tan­gle­ment, local operations, mea­sure­ments and classical feed­for­ward. A fault-tolerant logical operation requires additional protection. It may involve many physical qubits, repeated check mea­sure­ments, decoder output and correction tracking. The dis­tinc­tion matters whenever logical blocks live on different QPUs. A physical operation's fidelity therefore cannot substitute for an estimate of the failure prob­a­bil­i­ty of the complete encoded procedure.

What is a joint logical measurement?

Consider two encoded qubits, A and B. A joint mea­sure­ment of XAXB answers whether their logical X parities agree or disagree. Its result is a single sign, +1 or −1. This does not reveal each encoded qubit’s individual X value. Carefully chosen sequences of such parity mea­sure­ments, together with auxiliary logical states and Pauli-frame updates, can implement entangling operations without directly exposing the logical state to an unprotected gate.

The equation is compact; implementing the mea­sure­ment is not. In lattice surgery, the outcome is assembled from stabilizer in­for­ma­tion gathered over a fault-tolerant mea­sure­ment procedure. A boundary operation must be repeated and decoded so that physical mea­sure­ment errors do not im­me­di­ate­ly turn into incorrect logical feed­for­ward.

How lattice surgery works

Surface-code lattice surgery manipulates the stabilizer mea­sure­ments along boundaries of encoded patches. Joint logical mea­sure­ments such as X⊗X or Z⊗Z, together with prepa­ra­tion and feed­for­ward, can implement logical operations. If the patches are on different processors, mea­sure­ments across the joining boundary need a physical remote-in­ter­ac­tion protocol.

How distribution changes the seam

When the two patches live on different QPUs, a check along the joining seam can involve physical qubits that cannot interact directly. An en­tan­gle­ment-assisted mea­sure­ment circuit replaces the local check circuit. Its failures can manifest as data errors, mea­sure­ment errors, or correlated detector events. The effective seam noise therefore depends on the whole procedure, not merely the original Bell-pair infidelity.

Our dis­trib­uted lattice-surgery analysis isolates how noise along the seam changes logical per­for­mance for a specified XX-merge geometry. The important interpretation is comparative: an increase in seam noise can change which error chains dominate the logical failure prob­a­bil­i­ty and whether increasing a geometric parameter gives the expected protection. The result is not a universal statement about every network protocol.

The seam changes the logical noise

The boundary shared by two patches is often called a seam. A remote seam may be noisier than the rest of the code because it relies on imperfect Bell pairs and additional com­mu­ni­ca­tion. Our study of dis­trib­uted lattice surgery considers an XX-merge of rotated surface-code patches, with a geometry that tracks the bulk and seam contributions to logical errors. The resulting finite-size analysis is intended to char­ac­ter­ize a specific logical primitive under stated as­sump­tions.

The fidelity of the remote resource alone does not determine the logical outcome. Bell-pair generation may take time, causing data qubits to wait while undergoing memory noise. Limited com­mu­ni­ca­tion qubits can also force syndrome mea­sure­ments to be serialized. This creates a fidelity–latency–resource tradeoff that must be evaluated at logical level.

Spatial and temporal protection

In a code-capacity picture, distance describes the minimum weight of a logical Pauli operator. A surgery procedure is a circuit that extends through time. A faulty check readout may appear as a detection event between mea­sure­ment rounds, and repeated mea­sure­ments allow a decoder to dis­tin­guish physical faults from readout faults. The effective protection of a merge therefore depends on both its patch geometry and its syndrome history.

For a dis­trib­uted seam, the logical failure mechanisms are especially sensitive to the remote protocol. A Bell-pair imperfection can translate to data or readout errors; a late pair can add idle errors; a shared failure event can produce correlated detector outcomes. Simply labeling the in­ter­con­nect with a physical fidelity does not reveal which of these mechanisms dominates the decoded logical operation.

To compare two interfaces meaningfully, one should fix the same encoded operation and target error budget, then measure its failure prob­a­bil­i­ty, latency dis­tri­bu­tion, consumed en­tan­gle­ment and com­mu­ni­ca­tion-qubit occupancy. Even when a more elaborate purification procedure produces a better pair, the extra waiting could erode its advantage. It is the complete, decoded logical in­struc­tion that matters.

Time is part of the logical gadget

A logical merge has both spatial and temporal extent. If a remote check must be performed repeatedly and en­tan­gle­ment generation is prob­a­bilis­tic, the syndrome schedule can stall. That stall matters even if the Bell pair that eventually arrives is high fidelity: data continue to accumulate memory errors while awaiting the next operation.

For useful ar­chi­tec­ture comparisons, one should report the failure prob­a­bil­i­ty of a complete joint mea­sure­ment together with its latency and resource cost. Two protocols may achieve similar physical gate fidelity but have different logical error probabilities because one introduces longer memory exposure or more correlated errors.

Code-specific logical instruction sets

The choice of code also matters. Some logical gates may be trans­ver­sal, whereas others require surgery, injection, code conversion or special ancillary states. The Eastin–Knill restriction rules out a universal trans­ver­sal set for the relevant class of finite-dimensional error-detecting codes. A dis­trib­uted compiler cannot therefore assume that all logical in­struc­tions use the same remote-gate pattern.

Beyond a single code family

Lattice surgery is not the only way to interact logically encoded blocks. Depending on the code, al­ter­na­tives include trans­ver­sal logical gates, code switching, tele­por­ta­tion through encoded resources and magic-state-assisted non-Clifford operations. These al­ter­na­tives place com­mu­ni­ca­tion and ancilla demands in different places. A compiler must know what operations the chosen code actually supports rather than simply trans­lat­ing every high-level gate into the same remote physical primitive.

The architectural question

For me, the useful abstraction is a logical interface contract: its supported operation, code compatibility, required entangled resources, space-time schedule, decoder as­sump­tions and logical failure behavior. Once interfaces are char­ac­ter­ized this way, modular ar­chi­tec­tures can be compared as systems rather than as collections of nominally equivalent Bell links.

Research outlook

For comparing modular ar­chi­tec­tures, I would measure one complete logical in­struc­tion: the fault-tolerant circuit, en­tan­gle­ment consumption, correction rounds, time and failure prob­a­bil­i­ty. A good remote physical gate is only the beginning of that analysis. Reporting the logical in­struc­tion's latency dis­tri­bu­tion is also important because a slow remote interface can introduce additional idle errors elsewhere in the com­pu­ta­tion.
