Compilation and scheduling · November 2026 · 10 min read

From logical circuits to networked execution

Why mapping a logical circuit is more than minimizing remote gates

A logical quantum circuit is an abstract program. A real modular quantum computer has a limited number of encoded blocks, check ancillas, entanglement-generation ports and communication links. Translating the logical program into an executable fault-tolerant schedule requires an architecture-aware compilation stack.

The right level of compilation

Gate partitioning is a useful starting point, but a fault-tolerant instruction may be a complex gadget rather than a single physical gate. A code's supported logical gates must first be determined. A parity measurement or code-surgery operation has its own ancillary qubits, repeated measurements and decoding dependencies. These details determine what the network needs to deliver.

Five connected stages

01

Logical program: gate dependencies and target reliability.

02

Code-aware lowering: supported logical gadgets and ancillas.

03

Placement: assign encoded blocks and resources to QPUs.

04

Scheduling: allocate entanglement, communication ports and feedforward.

05

Evaluation: logical failure, completion time and resource usage.

The stages are coupled: placement changes remote-gate demand; scheduling changes memory waiting; waiting changes the error model and potentially the required code distance. This makes a one-way compiler that ignores physical timing inadequate for many distributed fault-tolerant workloads.

Network operations are not free

Our scheduling work investigated resource-limited network operations following partitioning, comparing constrained scheduling approaches with heuristic methods. A key lesson is that network dependencies and scarce resources must be represented explicitly. Recent work on network constraints in distributed FTQC likewise shows why finite entanglement rates and bandwidth competition matter for fault-tolerant execution.

Entanglement is a resource with a lifetime. Producing Bell pairs early can reduce stalls but increases storage exposure; generating them just in time can reduce aging but leave the computation waiting. Work on quantum-switch distillation policies illustrates how fidelity, throughput and waiting are interdependent.

Research outlook

I envision a compiler that outputs not only a schedule but an auditable reliability-and-resource report. The relevant objective is a tradeoff among logical error rate, makespan, communication load and ancillary resources, rather than simply minimizing the number of remote CNOTs.

A simple example of why minimizing remote gates can mislead

Consider a logical circuit with several operations between two encoded blocks. Placing those blocks together might remove many remote interactions, but may exceed one processor's data-qubit or ancilla capacity. Distributing them can make every interaction nonlocal. A third option may place frequently interacting blocks near shared communication resources while parallelizing unrelated operations elsewhere. None of these choices can be evaluated from a remote-gate count alone.

Logical operations are compound instructions

The compiler should not assume a logical CNOT is a single operation with fixed duration. For surface-code blocks it may be realized through joint measurements and feedforward. For other code families it could use a transversal operation or a dedicated fault-tolerant gadget. A non-Clifford logical gate may require a prepared ancilla resource and additional distillation or verification. These alternatives differ in qubit occupancy, communication demand, and sensitivity to noise.

Therefore, code-aware lowering comes before resource scheduling. It provides a dependency graph of physical and logical subroutines that the scheduler can actually execute. Network transport, storage of entanglement and classical feedforward should be represented as first-class resources—not a hidden constant added to each remote gate.

Finite resources create queueing and contention

A quantum switch cannot necessarily satisfy all remote requests simultaneously. Each link may have a finite Bell-pair generation rate, and a QPU may have only a few communication qubits. If the scheduler allows unlimited parallel remote operations, it can report a makespan no real hardware can achieve.

The distinction between an average generation time and a guaranteed deadline is important. A stochastic protocol can have a reasonable mean waiting time but a long tail. Repeated rounds of error correction may then require buffering, adaptive scheduling or a maximum retry policy. Each such choice changes how long physical data are exposed to memory noise.

How I would organize the compiler

I would build around explicit interfaces: a code library declares supported logical instructions and gadgets; an architecture model declares processor, memory and communication resources; a network model declares entanglement quality and delivery statistics; and a simulator estimates logical error and resource usage. The compiler can then compare feasible mappings and schedules, not merely circuit partitions.

For research evaluation, I would report logical failure, completion time, Bell pairs consumed (including failed attempts), communication-qubit occupation, ancilla resources and classical processing requirements. This avoids presenting an apparently faster schedule that succeeds only because the model ignores part of the error-correction workload.

From a program to an executable fault-tolerant plan

A distributed compiler cannot be understood only as a circuit partitioner. A logical circuit is made of encoded operations, each of which may require many physical gates, ancillas, syndrome measurements and classical feedforward. The available logical instructions depend on the chosen error-correcting code. A parity-measurement procedure for surface-code patches is not equivalent to a transversal operation on another code; non-Clifford gates may introduce further resource-state requirements.

This suggests a broad compilation pipeline: first determine the logical instruction set supported by the code, then lower the algorithm into implementable fault-tolerant gadgets, assign logical data and ancillary resources to processors, reserve communication resources, and assess the resulting logical reliability. The purpose is not to assume one perfect remote gate for every abstract gate, but to account for how the logical instruction is actually implemented.

Why the network changes the schedule

Consider two QPUs with a limited number of communication qubits. Bell pairs may be generated probabilistically; requests may compete for switch ports; and storing an already prepared pair may introduce memory errors. One remote logical procedure may have to wait while another consumes the available link capacity. Assigning a constant cost to every cross-QPU gate hides this dependency.

Likewise, the apparently best partition can depend on the application. A program with many independent local operations benefits from parallelism; a program dominated by repeated interactions among a few logical blocks may be better served by a different mapping and more concentrated communication resources. A compiler should evaluate the circuit's structure, not merely count the number of remote interactions.

What would a good compiler optimize?

Completion time, logical error, communication usage and physical-qubit occupancy form a tradeoff. My research perspective

I see the opportunity in a compiler that explains how an algorithm becomes a fault-tolerant execution on a networked architecture. A code library defines supported logical primitives; a hardware model declares available qubits and interactions; a network service describes entanglement delivery; and an evaluator provides logical-error and resource estimates. The system can then compare different code families and modular configurations on a fair basis. The broader aim is a reproducible connection between abstract logical programs and realistic distributed hardware—not merely a reduction in remote-gate count.
